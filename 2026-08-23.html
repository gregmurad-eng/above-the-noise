Lead Story

MCP's new roadmap moves agent identity off API keys and unifies transport on HTTP

— Model Context Protocol Blog[1]

The MCP maintainers published a new roadmap on August 22, signed by lead maintainers David Soria Parra and Den Delimarsky, that names five priority areas for the next specification cycle: agentic messaging primitives, HTTP-native transport unification, agent identity and enterprise security, improved primitives (progressive tool discovery and standardised tool results), and SDK developer experience.[1] The document commits to expedited SEP review for proposals inside those areas and identifies two Agent Identity WG proposals already in active review: SEP-1932 for Demonstrating Proof of Possession (DPoP), and SEP-1933 for Workload Identity Federation.[1][2]

The read for anyone shipping an MCP server today: static-secret authentication is being deliberately retired. DPoP is the OAuth-adjacent mechanism that binds an access token to a key held by the caller, so a stolen bearer token cannot be replayed from another machine. Workload Identity Federation is how an agent proves it is calling on behalf of a specific user in a specific runtime, rather than as a shared service principal with a long-lived key. Read together, they answer the two enterprise objections that have stalled MCP rollouts inside regulated shops all summer: "which agent did this call?" and "what happens when the key leaks?"

The transport story is the other half. The 2026-07-28 spec already made MCP servers stateless — each request carries what it needs, and a plain round-robin load balancer can front them — and the new roadmap collapses stdio-local and remote deployments onto the same HTTP-native transport model.[2] That removes the last mode-switching branch from SDK code and lets the same server binary sit behind a Kubernetes ingress, a laptop tray icon, or a Cloudflare Worker without a config split. Progressive discovery lands in the same cycle so a tool catalogue of a few hundred entries stops eating the model's context window on first connect.

What is not in this roadmap matters as much as what is. There is no capability-negotiation revamp, no new primitive for streaming multi-modal payloads, and no push to broaden the language of the spec beyond agent-to-tool. This is a hardening pass, not a widening one. The maintainers are betting that enterprise readiness — identity, audit, gateway behaviour, portable configuration — is what unblocks the next 12 months of adoption, and that the 97M-installs figure from the June dev summit is already the ceiling until those blockers move.[2]

So what: if you maintain an MCP server, mark DPoP (SEP-1932) and Workload Identity Federation (SEP-1933) as the next two hardening items on your Q4 roadmap — every enterprise buyer's security review after October will ask for both by name, and shipping ahead of the SDK is the cheapest time to do it.
